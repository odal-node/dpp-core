Every pull request merged since v0.24.0 is traced to the CHANGELOG entry that describes it, every entry's claims are checked against the code at the release commit, and every issue those pull requests closed is checked against what it asked for. Corrections land in `CHANGELOG.md` in the same change as this record, before the release. [`RELEASE.md`](../RELEASE.md) makes this record part of every release.

- **Range:** `v0.24.0` (`0cd71cb7`) to `main` at `e8ca36de`.
- **Checked against:** `main` at `e8ca36de`, tree `24b70d0e`. `just check` passed on that exact tree (2975 of 2975 in nextest, and the recorded checked tree is `24b70d0e`), before this record was written. The hosted run on that commit passed: CI and twelve other workflows (the AAS, COSE, GS1, JAdES, JOSE, JSON-LD, SD-JWT and Token Status List oracles, the W3C DID suite, the W3C VC-JOSE-COSE suite, the Wasm build and the workflow lint). The release pull request adds the version, which is still 0.24.0 in every manifest, and the release heading.
- **Date:** 2026-11-24.

## How each claim was checked

A claim is **verified** when the code at the release commit does what it says. Evidence is one of:

- the source location that implements it;
- a test that pins it, by name (every test named below is in the suite that passed on this tree);
- a measurement, where the claim is a number.

Section 2 gives each entry one of three verdicts. **Verified** means each sentence of the entry was held to one of those. **Verified, corrected** means the same, and an error was found and is corrected in this change. **Names and behaviour pinned** means every name, signature and variant the entry mentions was found in the code and its principal behaviour is pinned by a named test, but one or more sentences were not read to the last detail; the entry says which.

What an act, a standard or a draft says is held to the code's own citation of it. No RFC, W3C text or draft was re-read for the entries, so an entry's reading of one is verified as far as the code that cites it and no further. The register rows are re-read at source in section 4.

Every backticked path and identifier in the `[Unreleased]` section was also looked up mechanically in the tree outside the CHANGELOG. Of 411, 353 appear verbatim. Of the other 53, 40 appear by their last path segment: a `Type::member` or `module::item` written with its arguments or its module path, such as `jws::ES256_ALG`, whose constant is re-exported at the `jws` root (`jws/mod.rs:41`), or `ProductGroupAccessPolicy::concealable_members(path, scope)`. The remaining 13 are not names that are meant to exist: six are names the entries say are removed (`verify_eddsa`, `verify_eddsa(jws, public_key_b64)`, `public_key_jwk`, `jwk_thumbprint`, `JoseError::KeyBindingUnsupported`, `JoseError::DisclosedCriticalClaim`); two are a call form with a struct literal (`&PinnedKey { alg: "EdDSA", public_key_b64: &key }`) and a JSON shape (`{"field", "message"}`); two are JWK text (`crv: P-256`, `crv: P-384`); one is the error text `ES256 signature must be 64 bytes`, which the code builds from a label and a length (`jws/error.rs:28`) and a test pins (`a_wrong_length_signature_downcasts_to_its_error_under_both_algorithms`); and two are fragments of prose that the entry markup split (`** create a key of either algorithm.` and `. For ES384 and ES512 it reads`). No entry names a type, function or variant that does not exist. One name is wrong in kind, not in existence: `VerifiedSign1::cwt_claims` (C46) is a public field and the entry said it "returns" the claims.
