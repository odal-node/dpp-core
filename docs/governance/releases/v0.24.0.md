Corrections land in `CHANGELOG.md` in the same change as this record, before the release. [`RELEASE.md`](../RELEASE.md) makes this record part of every release.

- **Date:** 2026-11-13.

## How each claim was checked

A claim is **verified** when the code at the release commit does what it says. Evidence is one of:

- the source location that implements it;
- a test that pins it, by name (every test named below is in a suite that passed on 2026-11-13: `just check`, 2318 of 2318 in nextest and `EXIT=0`, run on the tree before anything was written and again after the CHANGELOG corrections, with this record in place);
- a measurement, where the claim is a number.

What an act says is held to the code's own citation of it (the `COMPLIANCE-PIN` blocks and the quoted text in doc comments). The Official Journal was not re-read for this record, so an entry's reading of an act is verified as far as the code that cites it, and no further.

Every backticked path and identifier in the `[Unreleased]` section was also checked mechanically to exist outside the CHANGELOG. Of 213, 181 do. The other 32 do not appear verbatim. 31 are legitimate: seven names the entries describe as removed or replaced (`chain.transfers`, `DerivationEdge::transfer: Option<TransferEvidence>`, `EolEvent::requires_derogation()`, `ProductGroup::UnsoldGoods`, `ProductGroupData::UnsoldGoods`, `SubstantiationDefect::NoTransfer`, and the call `determinable_for("unsold-goods")`, whose key is the removed group); a message template (`line{n}Reason`, which the code builds as `line{i}Reason`); two result shorthands (`Ok(SubstantiationBasis)`, `Err(SubstantiationDefect)`); two module paths (`lineage::evidence`, `lineage::input`); nineteen `Type::member` or call forms with the arguments elided or renamed, each of whose members exists (for instance `dpp_aas::build_unsold_goods_environment(report, name, value)`, whose parameters are `report`, `asset_name` and `asset_value`); and the 32nd, a struct written as a literal, which was the one finding and is corrected under C05. Three more appear only outside the code: `Passport::commodity_code` (a field), `repairabilityScore/overall` (the JSON path notation of `SCHEMA-CHANGES.md`) and `SubstantiationFinding` (a removed name, which only the 0.23.0 record still names). Of the paths, `schemas/unsold-goods/` is the place v2.0.0 moved from, so it is gone by design.

**#579 against its locked decision.** The decision's scope, item by item:

- **One check, used twice.** `validate` is the check. `initiate_transfer` runs it on the existing records followed by the new one, and `Deserialize` runs it on the whole chain. It requires the chain's `passport_id`, a `from_operator` equal to the operator the completed records before it left in place, and, in place of "at most one pending record", that no record follows a pending one (below).
- **Check on read.** `#[serde(try_from = "TransferChainRaw")]` through a private raw shape with today's field names, so the wire format is unchanged. The error is `TransferError::InvalidChain`, which names the passport, the index and the `transfer_id` of the record, and the reason. A stored chain under the old `toSignature` key still reads (`a_valid_stored_chain_under_the_old_acceptance_key_still_reads`).
- **`transfers` private.** `records()` and `pending()` read it, and `complete_pending`, `cancel_pending` and `reject_pending` each delegate to the record's own transition on a copy, refuse when nothing is pending, and leave the chain as it was on an error.
- **The check on `TransferRecord`'s public fields.** The decision asked whether they can break the invariant through the new methods. Review of #597 found one: a record with `completed_at` and a `from_signature` but no acceptance attestation had one outcome, so it passed, and `reject_pending` could then add a second. `f02a64f` closes it by refusing a `completed_at` without both signatures (`no_pending_method_leaves_a_chain_that_cannot_be_read_back`).
- **Documentation.** C14 is under Breaking with a migration note, which says the outgoing `from_signature` is set before `initiate_transfer`. That is true: the only method that touches a record in the chain, `complete_pending`, sets the attestation and nothing else. `PERSISTED-SHAPES.md` does not list the chain, so the decision's conditional line is not owed.
- **Tests.** The decision's three read cases and its two method cases are `a_stored_chain_with_a_record_for_another_passport_is_refused`, `a_stored_chain_with_a_broken_operator_sequence_is_refused`, `a_stored_chain_with_two_pending_records_is_refused`, `a_chain_built_through_the_methods_round_trips_unchanged` and `each_pending_method_refuses_when_nothing_is_pending_and_leaves_the_chain_alone`.

The PR body names three points beyond the decision's wording, and a fourth came from review. Each is in the code and pinned:

- **No record follows a pending one,** in place of "at most one pending record". The weaker rule lets a completed record follow a pending one, which `initiate_transfer` already refused: `a_stored_chain_with_a_completed_record_after_a_pending_one_is_refused`.
- **`passport_id` and `original_operator` are closed with `transfers`.** `just semver` lists all three as removed public fields.
- **A record with more than one outcome is refused,** reusing `InvalidState` with the action "record more than one outcome", and `TransferRecord` is unchanged: `a_stored_record_with_two_outcomes_is_refused_on_read`, `initiate_transfer_refuses_a_record_with_two_outcomes_and_leaves_the_chain_alone`.
- **A completion without both signatures is refused** (`f02a64f`): `a_stored_completion_without_both_signatures_is_refused_on_read`, `initiate_transfer_refuses_a_completion_without_both_signatures_and_leaves_the_chain_alone`.
